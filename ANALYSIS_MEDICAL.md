## 2. Что делает каждый модуль

### 2.1 `sh_grm_medical.lua` (ядро медкарт, `GRM.Medical`)
- **Хранение:** `data/grm_medcards.json` — карты, ключ = `CharacterKey` (`SteamID64:charN`),
  чтение через `jsonT(..., ignoreConversions=true)` (урок находки 65). Карантин при битом файле,
  миграция старых ключей.
- **Поля карты:** `name, blood, allergies, chronic, fitnessCategory, entries[]`.
- **Записи (`EntryKinds`):** diagnosis / note / vitals / prescription / operation / issue
  (служебная «выдача карты»).
- **Доступ (`MD.CanTreat`):** суперадмин; иначе фракция из `MD.Cfg.factions`
  (enabled + роли + отделы) — настраивается в `/medcards → Доступ`.
- **API:** `MD.CardOf(key)` (авто-создание пустой карты), `MD.SaveCards`, `MD.CanTreat`,
  `MD.ViewIssued`, `MD.HandleChat`, `MD.BloodTypes`, `MD.FitnessCategories`, `MD.EntryKinds`.
- **Физическая карта (v1.1.0):** кнопка «Выдать карту на руки» → предмет `medcard` в инвентарь
  (модель clipboard, дропается/подбирается, `issued` в карте + запись kind=issue).
- **Команды:** `/medcards` `/mycard` (и консоль `grm_medcards`).

### 2.2 `sh_grm_medical_full.lua` (лечение, `GRM.MedicalFull`)
- **Статусы пациента:** bleed / pain / infection / poison / addiction (тикер Think,
  кровотечение наносит урон, инфекция растёт).
- **Препараты (крафт):** painkillers / antibiotics / adrenaline / detox / advanced kit —
  регистрируются в `GRM.Inventory` + use-обработчики.
- **`/diagnose`** — медик сканирует цель и видит статусы.
- **Зависимость:** `GRM.Narcotics.ClearAddiction` (детокс), `GRM.Inventory`.

### 2.3 `grm_comp_medical` (компьютер госпиталя)
- `CanManage` — медики (по имени фракции или `GRM.Medical.CanTreat`).
- Вкладки: **«Картотека пациентов»** (редактор: ФИО, группа крови, ВВК, аллергии, хронические,
  журнал приёмов, «Сохранить», «Выдать физ. карту»), **«Реестр пациентов госпиталя»** (поиск).
- Сохранение через авторитарный `MD.SaveCards`.

### 2.4 `grm_med_lab` (лаборатория)
- Энтити «Медицинская лаборатория» (`LabType="med"`), `Use → GRM.NarcCraft.OpenLab(ply, "med", self)` —
  крафт препаратов из `GRM.MedicalFull.Recipes`.

### 2.5 Документ «медкарта» + обыск
- `sh_grm_documents.lua`: `sendOwnDoc(ply, "medcard")` → `GRM.Medical.CardOf(cardKey)` →
  двухфазный рендер `openMedCardUI` (обложка Минздрава ⇄ разворот: группа, ВВК, аллергии,
  хронические, журнал). Команды `/medcard` `/showmedcard`.
- `weapon_grm_search`: строка «Медкарта: группа/категория» в досье.

## 3. Ключи и потоки данных

- **Единый ключ — CharacterKey** (`GRM.Identity.CharacterKey`), одинаково в `sh_grm_medical.lua`
  (`identityKey`), `grm_comp_medical` (передаёт `GRM.Identity.CharacterKey`) и `sh_grm_documents.lua`
  (`getCharKey`). **Совпадает — рассинхрона по ключу нет.**
- Поток: врач (`/medcards` или `grm_comp_medical`) → `MD.Cards[key]` → `data/grm_medcards.json`
  → документ/обыск читают ту же карту.

## 4. Найденные проблемы и расхождения

1. **Группа крови — два несовместимых справочника (реальный дефект).**
   `grm_comp_medical/cl_init.lua` держит СВОЙ хардкод-список: `I (0) Rh+`, `II (A) Rh+` … `IV (AB) Rh-`
   (ноль в «(0)», дефис-минус). Ядро `MD.BloodTypes` = `O(I) Rh+`, `A(II) Rh+` … `AB(IV) Rh−`
   (буква O, тире U+2212 «−», порядок O/A/B/AB). Карта, заведённая в компьютере, хранит строку
   одного формата, заведённая в `/medcards` — другого. Реестр просто печатает `c.blood` как есть.
   → **Унифицировать на `GRM.Medical.BloodTypes`** (компьютер должен брать список из ядра).
2. **Категория годности ВВК — расходящиеся формулировки.**
   Компьютер: `В — Ограниченно годен к службе (запас)`, `Г — Временно не годен (отсрочка на лечение)`,
   `Д — Не годен к военной службе (освобождён)`. Ядро `MD.FitnessCategories`: `В — Ограниченно годен
   к службе`, `Г — Временно не годен (на период лечения)`, `Д — Не годен к военной службе`.
   → тот же дефект «два справочника», но мягче (совпадает буква категории А–Д).
3. **Обыск читает карту с легаси-фолбэком.** `weapon_grm_search/init.lua:142`:
   `GRM.Medical.Cards[charKey] or GRM.Medical.Cards[target:SteamID64()]`. Карты хранятся по
   CharacterKey (`…:charN`), поэтому второй аргумент (`SteamID64()` без суффикса) совпадает только
   со старыми записями до миграции. Не ломает показ, но фолбэк почти всегда мёртв —
   можно убрать/заменить на `GRM.Medical.CardOf(charKey)`.
4. **Пустая карта создаётся автоматически.** `MD.CardOf` при отсутствии записи сразу создаёт
   пустышку (и она попадает в реестр). В обыске/документе это выглядит как «медкарта заведена»,
   хотя врач её не заполнял. Для отображения стоит различать «не заведена» (нет записи в файле)
   и «заведена, но пустая».
5. **Двойной UI редактирования** (`/medcards` и `grm_comp_medical`) с пересекающимся функционалом
   и независимой вёрсткой — поддерживать надо два места. Рекомендуется один общий «редактор карты»
   (компьютер — основной, `/medcards` — мобильный), оба поверх `MD`.
6. **Категория годности в документах** рендерится как сырая строка `card.fitnessCategory` —
   при смене формулировок в ядре документ и компьютер должны показывать одинаково (решается п.2).

---

## 5. Рекомендации

1. **Один источник справочников**: `GRM.Medical.BloodTypes` и `GRM.Medical.FitnessCategories`
   использовать во всех UI (компьютер, `/medcards`, документ). Убрать хардкод в `grm_comp_medical`.
2. **Миграция** уже заведённых карт: нормализовать `blood` (оба формата → один) и `fitnessCategory`
   (по букве А–Д) при загрузке `MD.LoadCards`.
3. **«Не заведена»**: `MD.HasCard(key)` без авто-создания — для обыска/документа.
4. **Обыск**: заменить легаси-фолбэк на `GRM.Medical.CardOf(charKey)`.
