# Концепция: собственный инструмент перма пропов «GRM Perm Tool»

**Дата:** 2026-08-13 · **Статус:** концепция к согласованию, код не изменён
**Область:** перм-система (`sh_grm_perm_entities.lua`), проп-протектор (`sh_grm_prop_protect.lua`),
служебный инструмент (`grm_service_tool.lua`), FFD-двери, фракционные права

---

## 1. Что есть сейчас

| Подсистема | Файл | Состояние |
|---|---|---|
| Ядро перма | `lua/autorun/sh_grm_perm_entities.lua` (552 стр., v1.5.0) | Работает: база `data/grm_perm_entities.json`, спавн на `InitPostEntity`/`PostCleanupMap` |

### Как выглядит запись базы сегодня

```lua
{ map = "gm_construct", class = "grm_keypad", model = "models/...",
  pos = {x=..., y=..., z=...}, ang = {p=..., y=..., r=...}, data = { ... } }
```

Файл — плоский **массив** таких записей. Лимит `PERM_MAX = 256` на карту, дедуп и поиск — по
классу + радиусу `PERM_RANGE = 6` юнитов.

## 2. Дефекты и архитектурные проблемы

### Блокирующие

**Д17. `GRM.Perm.Add` / `GRM.Perm.Remove` не существуют.**
`grm_service_tool.lua:156` и `:210` вызывают их под `if GRM.Perm and GRM.Perm.Add then`.
Условие всегда ложно — **чекбокс «Автоматически сохранять на карте (Perm)» не делает ничего**,
а игрок при этом читает «(сохранено на карту)». После рестарта служебный компьютер исчезает.
Grep по всему `lua/` подтверждает: ни одного присваивания `GRM.Perm.*` в проекте нет.

**П1. Перм отбирает объект у владельца.**
`spawnAll()` для **каждой** воскрешённой записи зовёт `PP.MarkServerEntity(ent)`.
`PP.CanInteract` проверяет `IsServerEntity` **раньше** `IsOwner`, поэтому после рестарта
запермленная лидером фракции FFD-дверь принадлежит «Серверу»: владелец не может ни физганить,
ни тулить, ни снять её. Единственный выход — суперадмин. Запись перма вообще не хранит владельца.

**П2. `/permremove` удаляет объект.**
Команда одновременно снимает запись **и** делает `ent:Remove()`. Отдельной операции
«перестать сохранять, но оставить на карте» нет. Ошибка прицела = потерянный объект.

### Архитектурные

**П3. Поиск записи только по координатам.** Записи не имеют идентификатора. Если объект
сдвинули физганом дальше 6 юнитов — `/permremove` отвечает «записи нет», а после рестарта
объект возвращается на старое место (или воскресает вторым экземпляром рядом, если дрейф
превысил радиус `isOccupied`). Ручное лечение — только правка json.

**П4. Один делегат на класс.** `ffd_fading_door.lua:192/224` присваивает
`GRM.PermData.Extract["prop_physics"] = ...` напрямую. Любой второй потребитель того же
класса (а перм-тул для обычных пропов обязан им быть — цвет, материал, скин, заморозка)
молча затрёт FFD-двери или будет затёрт сам, в зависимости от порядка загрузки.

**П5. Перм ест лимит пропов.** `PP.countProps` считает все `prop_physics` персонажа,
включая запермленные. 150 запермленных дверей = игрок не может поставить ни одного пропа.

**П6. Два несогласованных списка классов.** `PERM_CLASSES` (перм) и `SERVER_CLASSES`
(протектор) пересекаются, но живут отдельно, оба — локальные таблицы, снаружи не расширяются.
Новый GRM-класс надо добавлять в два места, и об этом легко забыть.

**П7. Нет прав кроме суперадмина.** Пермить может только суперадмин. Лидер фракции не может
закрепить оборудование своего ведомства, хотя `grm_service_tool` ему это ставить разрешает.

**П8. Нет аудита.** Кто и когда запермил объект — известно только из логов консоли,
в базе этого нет.

### Мины, которые нельзя задеть

- Модули с **собственной** персистентностью: CCTV (`CCTV.SavePermanent`), `grm_vendor`
  (`data/grm_vendors/<map>.json`), логистика, автоперсистентные (`grm_server_rack`,
  `grm_antenna`, `grm_radio_station`, `grm_net_console`, `grm_loudspeaker`).
  Двойной перм = дубли объектов на карте.
- Временные сущности: `grm_item_drop`, `grm_money_drop`, `grm_ore_chunk`, `grm_mobile_line`,
  `grm_logistics_crate` — перм такого объекта превращает мусор в вечный мусор.
- Формат файла: на сервере накоплены рабочие json — **миграция обязательна и без потерь**.

## 3. Предлагаемое решение

Три слоя. Ядро остаётся там же, где было, тул — тонкий клиент над ядром.

```
  STOOL grm_perm_tool  ─┐
  grm_service_tool     ─┼─►  GRM.Perm (публичный API)  ─►  база grm_perm_entities.json
  другие модули        ─┘            │
                                     ├─►  GRM.PropProtect  (владение, защита, лимиты)
                                     └─►  GRM.PermData     (цепочки Extract/Apply)
```

### 3.1. Публичный API ядра — `GRM.Perm` (решает Д17, П6)

```lua
GRM.Perm.Add(ply, ent, opts)   -- "added" | "exists" | "limit" | "quota" | "noclass"
                               --  | "blacklist" | "denied" | "savefail" | "invalid"
GRM.Perm.Remove(ply, ent, deleteEnt)  -- "removed" | "notfound" | "denied"
GRM.Perm.Update(ply, ent)      -- "updated" | "added"  (позиция, угол, data)
GRM.Perm.IsPerm(ent)           -- bool
GRM.Perm.Info(ent)             -- запись базы или nil
GRM.Perm.ListForMap(map)       -- массив записей
GRM.Perm.CanManage(ply, ent)   -- bool, reason
GRM.Perm.IsPermable(ent)       -- bool, reason  (класс/чёрный список/автоперсистентность)
GRM.Perm.RegisterClass(class, opts)  -- расширение реестра снаружи
GRM.Perm.Classes / GRM.Perm.Blacklist
```

Сигнатуры `Add(ply, ent)` и `Remove(ply, ent)` выбраны **точно такими, как их уже зовёт**
`grm_service_tool.lua` — дефект Д17 закрывается без правки самого служебного тула.

`opts` = `{ ownerKind = "server"|"character"|"faction", freeze = true, label = "..." }`.

### 3.2. Расширение записи + миграция (решает П1, П3, П8)

Файл остаётся **плоским массивом** — старый `loadList()` продолжит его читать. Добавляются
только поля записи:

```lua
{
  -- было
  map, class, model, pos = {x,y,z}, ang = {p,y,r}, data = {...},
  -- стало дополнительно
  uid        = "p_1a2b3c4d",   -- стабильный ID записи
  ownerKind  = "server",       -- server | character | faction
  owner      = "",             -- CharacterKey владельца (для character)
  ownerName  = "",             -- отображаемое имя на момент перма
  faction    = "",             -- имя фракции (для faction)
  freeze     = true,           -- замораживать физику при воскрешении
  label      = "",             -- необязательная подпись для /permlist
  by         = "", byName = "",-- кто запермил (аудит)
  at         = 1770000000,     -- когда (os.time)
}
```

**Миграция (идемпотентная, при первой загрузке базы):**

1. Если хотя бы у одной записи нет `uid` → сначала бэкап
   `data/grm_perm_entities.bak.<os.time>.json` (только один раз, при наличии файла-бэкапа
   с тем же именем — пропуск).
2. Каждой записи без `uid` присваивается сгенерированный `uid`.
3. `ownerKind` отсутствует → `"server"` — это **ровно текущее поведение**, старые пермы
   продолжают быть серверным оборудованием, ничего не меняется.
4. `freeze` отсутствует → `true` (как сейчас — `EnableMotion(false)`).
5. Файл перезаписывается один раз; повторные запуски миграцию не выполняют.

Никакие существующие поля не переименовываются и не удаляются. Откат = вернуть `.bak`.

### 3.3. Синхронизация с проп-протектором (решает П1, П5)

Вводится третья категория владения — «перм игрока/фракции», между «серверным» и «своим пропом».

| Что | Сейчас | Станет |
|---|---|---|
| `ent._grmPerm` | «серверное оборудование» **и** «не чистить» одновременно | только «персистентный объект, не чистить» |
| `ent._grmPermKind` | — | `server` / `character` / `faction` |
| `ent._grmPermUID` | — | uid записи для точного поиска |

Правки в `sh_grm_prop_protect.lua` (минимальные, поведение по умолчанию сохраняется):

1. **`PP.IsServerEntity`** — `_grmPerm == true` считается серверным, **только если**
   `_grmPermKind` не задан или равен `"server"`. Старые пермы → `ownerKind="server"` → ведут себя
   как раньше, регрессии нет.
2. **`PP.CanInteract`** — новая ветка перед «чужой проп»: если объект перм-персонажа/фракции
   и игрок владелец (или член фракции с правом) → правила владельца, `remove` при этом
   всегда `false` (снять объект можно только тулом, чтобы запись не осиротела).
3. **`PP.countProps`** — пропускает `ent._grmPerm`, запермленные объекты не съедают `maxProps`.
4. **`cleanupProps` / `cleanupDisconnectedOwner`** — уже фильтруют `_grmPerm`, менять не нужно;
   важно, что перм-тул выставляет `_grmPerm` **для всех** видов владения, включая `character`.
5. **HUD владельца** — добавляется строка «Закреплено на карте (перм)» и имя того, кому
   объект принадлежит.

При воскрешении (`spawnAll`) вместо безусловного `MarkServerEntity`:

- `ownerKind == "server"` → `PP.MarkServerEntity(ent)` (как сейчас);
- `ownerKind == "character"` → восстанавливаются `GRM_PropOwnerCharacterKey` /
  `GRM_EntityOwnerCharacterKey` + NW-строки с именем из записи; `_grmPerm = true`;
- `ownerKind == "faction"` → владельцем считается фракция; доступ у членов с правом
  `perm_manage`, у остальных — как к серверному.

### 3.4. Цепочки делегатов данных (решает П4)

```lua
GRM.PermData.AddExtract(class, fn)  -- fn(ent) -> table|nil ; результаты мержатся
GRM.PermData.AddApply(class, fn)    -- fn(ent, data)        ; вызываются по очереди
```

Реализация в ядре перма (грузится как `autorun`, то есть раньше стулов), обёртка сохраняет
уже установленный делегат. Дополнительно `ffd_fading_door.lua` переводится с прямого
присваивания на `AddExtract`/`AddApply` — тогда порядок загрузки перестаёт что-либо решать,
а FFD-двери и перм-тул сосуществуют на одном классе `prop_physics`.

Перм-тул регистрирует для `prop_physics` собственный делегат, сохраняющий визуал и физику:

```lua
data.prop = { color = {r,g,b,a}, material = "", skin = 0, bodygroups = {...},
              frozen = true, solid = true, renderfx = 0, scale = 1 }
```

Ключи не пересекаются с `data.ffd` и `data.sliding` — мерж безопасен.

### 3.5. Реестр классов (решает П6)

Единая точка в ядре перма:

- `GRM.Perm.Classes` — публичный алиас `PERM_CLASSES`;
- `GRM.Perm.Blacklist` — **явный** чёрный список с человеческой причиной отказа:
  «у CCTV собственное сохранение», «временный объект», «модуль сохраняется сам».
  Отказ идёт с пояснением в чат, а не молча;
- `GRM.Perm.RegisterClass(class)` — сторонние модули регистрируют свои классы сами;
- хук `GRM_PermCanAdd(ply, ent)` — любой модуль может ветировать перм (возврат `false, "причина"`).

`SERVER_CLASSES` протектора не дублируется: перм-объект и так опознаётся по `_grmPerm`.

### 3.6. Права и квоты (решает П7)

| Роль | Что может |
|---|---|
| Суперадмин | всё: любой класс, любой владелец, лимит `PERM_MAX = 256` на карту |
| Лидер фракции / роль с правом `perm_manage` | пермить объекты своей фракции (`ownerKind = "faction"`), квота **32** записи на фракцию |
| Игрок | по умолчанию **запрещено**; включается конвар `grm_perm_players 1`, квота **8**, только `prop_physics` и только свои пропы |

В `GRM.FactionPerms.Permissions` добавляется `perm_manage = "Закрепление объектов на карте (перм)"`
— право сразу появится в существующем UI фракционных прав, отдельный интерфейс не нужен.

### 3.7. Инструмент `grm_perm_tool` (STOOL, категория GRM)

Оформление — по образцу `grm_service_tool.lua`.

| Действие | Поведение |
|---|---|
| **ЛКМ** | Запермить объект под прицелом. Если уже запермлен — обновить запись (позиция/угол/данные) |
| **ПКМ** | Информация: класс, uid, владелец, кто и когда запермил, сколько пермов на карте — в чат |
| **R (Reload)** | Снять перм. По умолчанию объект **остаётся** на карте; чекбокс «удалять объект» включает старое поведение `/permremove` |
| **Shift + ЛКМ** | Перм с текущей позицией «как есть», без заморозки (для подвижных объектов) |

C-панель:
- комбобокс «Владелец записи»: Сервер (оборудование) / Мой персонаж / Моя фракция;
- чекбокс «Заморозить физику при восстановлении» (по умолчанию вкл.);
- чекбокс «При снятии перма удалять объект» (по умолчанию **выкл.** — это и есть лечение П2);
- поле «Подпись» (`label`) — попадает в `/permlist`;
- кнопки: «Список пермов на карте», «Перезагрузить пермы», «Снять все мои пермы»;
- справка со списком классов, которые пермить нельзя, и почему.

Клиентский оверлей, пока тул в руках: над каждым перм-объектом в радиусе ~1200 юнитов —
рамка и подпись «ПЕРМ · класс · владелец». Данные приходят одним снимком по
`GRM_PermTool_Snapshot` при взятии тула и по кнопке обновления (не таймером, чтобы не грузить сеть).

### 3.8. Автообновление позиции (решает П3)

`PhysgunDrop` для объекта с `_grmPermUID`: дебаунс 1.5 с → обновление `pos`/`ang` в записи.
Подвинул запермленную дверь физганом — новое положение сохранилось само. Поиск записи идёт
по `uid`, координаты остаются только как fallback для незамигрированных записей.

### 3.9. Хуки для остальных модулей

`GRM_PermAdded(ply, ent, rec)`, `GRM_PermRemoved(ply, class, rec)`, `GRM_PermUpdated(ent, rec)`,
`GRM_PermRestored(ent, rec)` — последний вызывается после воскрешения на `InitPostEntity`,
чтобы модули (сигнализация, банк, электроника) могли доподключить объект к своим реестрам.

## 5. Порядок работ

1. **Ядро.** `GRM.Perm` API, uid, миграция базы + бэкап, `ownerKind`, чёрный список, цепочки
   делегатов, хуки. Тест `sim_perm_tool.lua`: миграция старой базы, идемпотентность,
   uid-поиск, квоты, отказы чёрного списка.
2. **Протектор.** Правки `IsServerEntity` / `CanInteract` / `countProps` / HUD.
   Прогон `sim_prop_protect` — он сейчас красный на `PP.IsManaged` (функции нет), заодно
   разбираем, чинить тест или вернуть функцию.
3. **Делегаты FFD.** Перевод на цепочку + `sim_ffdtools`, `sim_sliding_door` в регрессию.
4. **Инструмент.** STOOL + C-панель + оверлей.
5. **Права.** `perm_manage` в фракционных правах.
6. **Регрессия.** `sim_perm_upsert` (14/14 сейчас зелёный — обязан остаться), `sim_ffdtools`,
   `sim_sliding_door`, `sim_prop_protect`, `roundtrip_test`.
7. **Документация** (`PERM_SYSTEM.md`), сборка `dist/`, коммит, ссылки на архивы.

## 6. Вопросы к согласованию

1. **Кому разрешать перм?** Предложено: суперадмин всегда, лидер фракции с правом
   `perm_manage` — объекты фракции, обычный игрок — по умолчанию **нет**.
   Открывать ли игрокам перм своих пропов (например, 8 штук на персонажа)?
2. **Снятие перма по R:** по умолчанию **оставлять объект** на карте (безопаснее), удаление —
   галочкой. Согласны, или привычнее старое поведение `/permremove` (удалять сразу)?
3. **Судьба старых пермов после миграции:** все становятся `ownerKind = "server"`, то есть
   ведут себя ровно как сегодня. Нужна ли команда массового перевода части из них
   на фракции (например, `/permowner <фракция>` по прицелу)?
4. **Квоты:** 32 записи на фракцию, 256 на карту суммарно. Достаточно?
5. **Что делать со старыми чат-командами** `/permadd` и `/permremove`: оставить как есть
   (совместимость) или перевести на новое ядро с прежним поведением?
